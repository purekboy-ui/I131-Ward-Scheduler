# Engineer Handoff

## 1. 這個 repo 是什麼

這是一個 **前端展示原型**，目的是把 I-131 排程流程、欄位需求、畫面優先順序與權限規則整理給院內工程師接手。

目前沒有正式後端，也沒有正式登入流程。所有資料都存在前端記憶體內。

## 2. Live runtime

瀏覽器目前實際使用：

- `index.html`
- `styles.css`
- `app.js`

目前 repo 已把未使用的舊模組檔清掉，避免工程師誤判真正的 live runtime。

## 3. 主要資料來源

`app.js` 內目前用以下前端資料結構驅動畫面：

- `mockUsers`：帳號與角色
- `mockDoctors`：主治醫師清單
- `mockBookings`：住院與門診預約
- `mockAuditLogs`：操作紀錄
- `dateOverrides`：日期 x 床位開關

目前資料不會持久化到正式資料庫，重新整理後會回到程式內預設資料。

## 4. 目前角色模型

程式內保留四種角色：

| 角色代碼 | 顯示名稱 | 說明 |
| --- | --- | --- |
| `manager` | 管理員 | 可收單、可進後台、可維護帳號與床位 |
| `super_editor` | 排程管理 | 預留給進階排程角色 |
| `editor` | 一般使用者 | 可建立與維護自己可編輯的預約 |
| `viewer` | 檢視 | 僅查看 |

目前 demo 預設帳號只有：

- `admin / admin`
- `user / user`

## 5. 現在的核心業務規則

### 5.1 住院大劑量

1. 使用者從月曆選日期與床位建立預約。
2. 新建預約一律為 `待確認`。
3. 管理者核對欄位完整後才可改成 `已確認`。
4. `已確認` 後，一般使用者不能編輯、刪除、移動。
5. 床位開放狀態來自 `dateOverrides[date][bed]`。

### 5.2 門診小劑量

1. 不占住院床位。
2. 預設可排任何未來日期。
3. 新建一律先 `待確認`。
4. 收單後同樣鎖定一般使用者修改。

### 5.3 收單條件

管理者收單前必須至少有：

- 病歷號
- 病人姓名
- 劑量
- 主治醫師

## 6. UI 設計決策

這版 UI 不是走華麗儀表板，而是偏向 **高密度、低裝飾、方便人工核對**：

- 月曆優先看床位、病人、劑量、空床、未開床
- 預約管理以清單核對為主，弱化花俏 tag
- 後台把醫師、帳號、床位開關集中，避免空白浪費

## 7. 建議接手順序

1. **先讀** `docs/SYSTEM_WORKFLOW.md`
2. **再看** `docs/SCREEN_REFERENCE.md`
3. **確認 live runtime** 只在 `index.html + styles.css + app.js`
4. 把 `mock*` 資料改成正式 API / DB 存取
5. 以現有 SOP 為準補上後端權限、審計、登入

## 8. 正式化時的建議拆分

### 前端

- 保留目前資訊架構與欄位排序
- 將 `app.js` 拆為：
  - auth
  - bookings
  - calendar
  - admin
  - reports
  - audit

### 後端

建議至少拆出：

- `users`
- `doctors`
- `bookings`
- `bed_overrides`
- `audit_logs`

並讓以下動作走後端檢核：

- 收單
- 刪除預約
- 移動預約
- 切換床位開關
- 匯出報表

## 9. 安全提醒

這個 repo 是展示版，**不能直接拿來放真實病患資料**。目前不適合正式上線的原因包括：

- 帳密存在前端 mock data
- 沒有正式身份驗證
- 沒有後端權限檢核
- 沒有正式資料庫與備份
- 沒有院內資安整合

## 10. 驗收重點

院內工程師接手後，至少要先確認：

1. 住院 / 門診都能新建待確認預約
2. 管理者收單後會正確鎖定
3. 月曆在不捲動情況下可讀完整月
4. 5B / 6B 同日資訊不會被裁切
5. 後台醫師清單與各下拉選單同步
6. 預約管理頁能快速核對病人與劑量
